# 技术架构与内容存储设计

## 1. 项目目标

建设面向土耳其读者的土耳其语自动化新闻网站。系统从经过审核的新闻源获取新闻线索，进行去重、事实与来源检查、土耳其语编辑，再生成静态网页。

核心固定要求：

- 新闻扫描频率：每 30 分钟一次（每天最多 48 个计划周期）。
- 初期优先使用 GitHub 与 Cloudflare 免费资源。
- 网站采用静态生成，不提供注册、登录、会员或用户资料功能。
- 不因“自动化”而牺牲来源透明度、版权合规和重大新闻审核。
- 分阶段建设，每阶段测试通过并经项目所有者确认后再继续。

## 2. 初期技术选型

| 层 | 方案 | 用途 |
|---|---|---|
| 代码与内容版本管理 | GitHub 公共仓库 | 保存源代码、文章 Markdown、配置和审核记录 |
| 定时调度 | GitHub Actions | 每 30 分钟触发采集任务 |
| 内容存储 | Markdown + 分区 JSON 文件 | 文章正文、来源元数据、去重状态、审核状态 |
| 静态站点框架 | Astro + TypeScript | 构建快速、可索引的静态页面 |
| 样式 | CSS，后续视需要采用 Tailwind CSS | 响应式页面样式 |
| 静态站点部署 | Cloudflare Pages | 托管生成后的静态网站 |
| 静态站内搜索 | Pagefind（后续阶段评估） | 构建期生成搜索索引 |

初期不引入 D1、R2、Workers、独立服务器或传统 CMS。只有在真实需求和成本评估证明必要时，才讨论增加服务。

## 3. 数据库 / 内容存储决策

**初期不使用数据库。** Git 仓库作为内容源与轻量内容存储：

- 每篇新闻保存为独立 Markdown 文件，按年月分目录。
- 新闻源清单保存在 `data/sources.json`。
- 分类配置保存在 `data/categories.json`。
- 去重与来源运行状态使用按日期或来源分区的 JSON 文件，避免单个文件无限增长。
- 重大新闻待审内容与审核状态保存在仓库文件或 Pull Request 中。
- Astro 构建时读取这些文件并生成 HTML。

建议文章元数据字段（后续实现时再定稿）：

- `id`：稳定且唯一的内部 ID
- `title`：土耳其语编辑标题
- `summary`：原创土耳其语摘要
- `source_name`、`source_url`：来源名称和原文链接
- `source_published_at`：来源发布时间
- `collected_at`：采集时间（UTC）
- `category`、`tags`：分类与标签
- `status`：draft / review / published / rejected
- `importance`：normal / important / major
- `language`：默认 tr

### 无数据库方案的边界与风险

- Git 仓库不适合高并发写入或海量数据；初期需要限制保留规模并定期归档。
- Actions 可能并发运行，因此采集任务必须设置并发保护，并在提交前处理分支更新冲突。
- JSON 状态文件应分区写入，避免多个任务同时覆盖同一个大文件。
- 删除、修改文章会留下 Git 历史；不得将 Git 历史当作隐私数据删除机制。
- 若将来内容规模、查询复杂度或并发量超出文件方案能力，再单独评估数据库，不预先引入。

## 4. 采集与发布流程

计划流程：

1. Actions 定时启动，频率固定为每 30 分钟。
2. 读取启用的新闻源配置。
3. 获取 RSS / API 数据；记录来源、原文 URL、发布时间和采集时间。
4. 规范化 URL、标题和来源标识，执行去重。
5. 进行来源可信度、时间有效性、内容完整性检查。
6. 对可处理的内容生成土耳其语原创标题、摘要、分类和标签。
7. 检查摘要是否超出来源可支持的事实，保留来源链接。
8. 普通新闻可按规则自动发布；重要新闻要求多来源交叉核实；重大或敏感新闻进入人工审核。
9. 将内容保存为 Markdown / JSON 并提交到 Git。
10. 构建 Astro 静态网站并部署 Cloudflare Pages。

**注意：** GitHub Actions 的 cron 是尽力调度，不保证准点执行。工作流需要记录实际启动时间、成功率和延迟，并配置失败告警或可观察日志。

## 5. 部署策略与构建额度

计划由 GitHub Actions 执行构建，再通过 Cloudflare Pages Direct Upload 部署静态产物。

不建议在初期使用 Cloudflare Pages 的 Git 自动构建触发每次内容提交：30 分钟采集一次意味着理论上每月约 1,440 个周期，可能造成构建次数超过免费额度或不必要消耗。

Cloudflare Pages 项目创建时应确认采用 Direct Upload；Git 集成与 Direct Upload 的项目模式不能简单地事后互换。部署前需重新核实当时的产品限制、免费额度和 Wrangler 部署方式，并由项目所有者确认。

## 6. 安全与成本控制

- API Key、Cloudflare Token 等只能存入 GitHub Actions Secrets。
- 不在代码、日志、文章或提交记录中输出密钥。
- 默认不启用任何付费 API 或服务。
- AI 编辑接口属于可能产生费用的独立项目，必须先确认供应商、模型、单篇成本、月度上限和失败重试策略。
- 对采集与 AI 调用设置超时、重试上限、单轮处理数量上限和预算监控。
- 免费额度、定价和平台条款会变化，实施时必须复核官方最新说明。

## 7. 重大新闻审核

重大、突发、涉及伤亡或公共安全、选举、外交冲突及其他高风险新闻，不应仅凭单一来源自动发布。应进入人工审核流程。初期可通过 GitHub Pull Request 审核，不需要网站后台或数据库。

## 8. 明确不做的功能

初期不建设：

- 用户注册 / 登录 / 会员系统
- 评论、用户投稿或用户个人中心
- 数据库后台或复杂 CMS
- 未经授权的全文转载或图片镜像
- 未经项目所有者批准的付费 API、托管服务或订阅
